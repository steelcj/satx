# Multilingual Ingress Requirements

**Version.** v0.0.2, 2026-09-10. Supersedes *Ingress Requirements, SAT to Eleventy, Multilingual as Only Axis* v0.0.1.

**Scope.** What SAT must write into a Markdown file for Eleventy to build a multilingual site. Language is the only axis. Eleventy only. Where the values come from is covered by *Dublin Core 1.1 in the SAT Archive*.

**Direction.** One way. SAT is the source, the front matter is generated egress, Eleventy is the consumer. Nothing flows back.

**Status.** Describes a working implementation rather than a proposal. Every field below is emitted, consumed, and verified against a 22 page bilingual corpus.

## Changes in this version

- **Added `order`.** Menu sequence, resolved from the work so that both languages receive one value.
- **Added `navTitle`, `headerMenu`, `footerMenu`** as optional overrides read by the navigation builder.
- **Removed `menu`.** v0.0.1 carried `menu.order`, which could only ever describe the top level.
- **Recorded that hierarchy is NOT carried.** Ancestors and children were expected to need front matter fields. Building the consumer showed they do not, and the section explaining why is the most useful part of this revision.

## The governing rule

**The front matter carries facts. The configuration carries rules.**

A value belongs in front matter if a template cannot obtain it any other way. A value belongs in `eleventy.config.js` if it can be derived from what is already there, or from the set of built pages taken together.

The navigation work in this version sharpened the second half. A page's ancestors and children are derivable from the URLs of all pages, so they belong to a build-time collection rather than to any page's front matter.

Field presence across a 22 page corpus: `layout`, `permalink`, `title`, `date`, `lang`, `dir`, `sat`, `translations`, `dc` and `iri` on all 22; `order` on 10; `translationOf` on 10; `hreflang_default` on 2.

## Hierarchy is derived, not carried

This is the substantive finding of v0.0.2, and it reverses an assumption.

The expectation was that a page needing breadcrumbs must carry an `ancestors` array, and a section index must carry a `children` array, because a template cannot walk the archive. Both turned out to be unnecessary.

The hierarchy is already in `permalink`. Split every page's URL into segments, drop the language segment, and the nesting reconstructs itself. A build-time collection produces one tree per language, and three things fall out of it: the menu is the root's children, breadcrumbs are the ancestors of the current URL, and a section index is the current node's children.

So the ingress got smaller rather than larger. Nothing about hierarchy is authored, nothing is emitted, and nothing can drift from the paths, because the paths are the source.

The rule this establishes: **anything reconstructable from the set of all pages belongs to a collection, not to a page.** `translations` is the counterexample that proves it useful, since a page's siblings are not reconstructable from URLs and must be resolved by something that knows about works.

## Ordering

`order` is an integer, a work's position among its siblings.

**It is resolved from the work, not authored per expression.** "Projects before Areas" is a fact about the site's structure, identical in every language, so it belongs to the thing every language shares. Written into each language's page independently it would be one fact stored twice, able to drift, with the English and French menus disagreeing and nothing detecting it.

The generator holds it once and writes it into both expressions, so a template still reads a plain integer and needs to know nothing about works.

**Absence is meaningful.** A page with no `order` sorts after every page that has one, alphabetically by title, collated in the reading language. That default needs no declaration and matches what an editor sees in a directory listing.

The consequence is worth stating rather than discovering. The legal section, sorted this way, reads `Accessibility, Licensing, Privacy, Terms of Service` in English and `Accessibilité, Conditions d'utilisation, Licences, Politique de confidentialité` in French. As concepts those are different sequences. For a reference list that is correct, since a reader scanning an index expects their own alphabet. Where a sequence carries meaning and must hold across languages, the works get an `order` and the divergence disappears.

**Raw filesystem order is not an option.** `readdir` returns entries in neither creation nor alphabetical order, and Python, Node and `ls -U` each report a different sequence for the same directory. A menu built on it could differ between a laptop and a build server.

## Optional navigation overrides

Three fields the navigation builder reads, none of which the generator currently emits. They are specified because the consumer supports them and content will eventually need them.

**`navTitle`** replaces `title` in menus only. For a page whose full title is too long to sit in a nav bar.

**`headerMenu`** and **`footerMenu`** are booleans defaulting to true, so an ordinary page needs no front matter to be navigable. A page opts out rather than in, which means adding content cannot accidentally hide it.

All three are expression-level rather than work-level, because a nav label may reasonably differ in length between languages even when the title does not.

## Field notes

**`permalink` is carried, not computed.** The generator resolved it already, because the two language trees have independent shapes. Computing it again in configuration would put one rule in two implementations. Carrying it also lets a reader see where a file publishes without running the resolver.

**Top-level `date` is required.** Without it Eleventy falls back to file creation time, and every collection silently orders by when the generator last touched the file.

**DC elements are namespaced under `dc:`.** Eleventy defines `title`, `date`, `layout`, `permalink` and `tags` at the top level. A top-level `date` would be both the DC date and the sort key, which works until a document is published on one date and describes an event on another.

**`format` is `text/html`.** This block describes the page being built. The Markdown source is `text/markdown`, and that stays in the sidecar where it describes the source.

**`translations` includes self and is inverted at build time.** No page counts its own translations. Adding a language regenerates every page, which is safe because rebuild is total.

**`hreflang_default` appears on the home work only.** It names where to send a visitor whose language is not published, and that destination exists only where the root is a language selector. For any other work there is no language-neutral page, and naming the English one would assert that English is everyone's default.

**Language tags are lowercase and quoted.** Case carries no meaning in BCP 47, and under YAML 1.1 `no` is both a boolean and the ISO 639-1 code for Norwegian. Parse as YAML 1.2.

**`dir` is declared on the language, not derived from it.** Direction follows the script, and a language may be written in more than one.

## What the configuration provides

Two collections and six filters, none of which require additional front matter.

`byLanguage` groups pages by `lang`. `navTrees` builds one nested tree per language from the URLs.

`nodeFor` finds the current page's node, giving it its children. `ancestorsFor` gives the breadcrumb trail. `others` filters self out of `translations` for the switcher. `isUntranslated` detects a page with no counterpart. `jsonld` emits the graph. `isoDate` formats `lastmod` for the sitemap.

The home page is the tree root rather than one of its children, because its URL is the language archive itself. A menu template must render the root explicitly before iterating its children, or the home link disappears.

## Verified

25 files built from a 22 page bilingual corpus, plus a language selector, a sitemap and a robots file. Eight output assertions pass: no duplicate hreflang tags, every hreflang relation reciprocal, every JSON-LD block parsing unescaped, every canonical absolute, sitemap and page head agreeing, one host throughout, and a non-empty build.

## Open

**`localeLabel` for the root selector.** The selector renders `en-ca · fr-ca` rather than language names, because it has no `translations` block to carry labels. Either the generator emits per-page labels, or a `_data/languages.json` is emitted from the language registry.

**Assets.** No passthrough copy is configured, so there is nowhere for a stylesheet or an image to live. SAT colocates a resource's assets in a `<name>.assets/` directory beside it, and the ingress says nothing about how those reach the built site or what URL they receive. Site-wide assets are a separate case, since they belong to no resource.

**`dc.subject` carries bare strings.** Subjects are concepts with labels per language, and everything else that is a concept carries an identifier. A French page and an English page currently share a subject only by string coincidence.

**Stale translations.** `translationOf.stale` is carried and nothing consumes it. Whether a stale page renders with a notice, is held back, or fails the build is archive policy and is not decided.
